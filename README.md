# Apploy Probe — диагностический сайт для проверки хостинга

Это небольшой Node.js-проект без npm-зависимостей. Собирает **только технические характеристики** и результаты тестов по кнопке. Не трогает реальные вебхуки, не сохраняет персональные данные, не отправляет отчёты куда-либо автоматически.

## Как запустить локально

1. Установи Node.js 20+.
2. Необязательно: установи переменную окружения `DIAG_TOKEN` с длинным случайным значением. Если не установить, приложение создаст временный токен при запуске и выведет его в приватные логи контейнера.
3. Запусти: `npm start`.
4. Открой `http://localhost:3000` и введи тот же токен в поле на странице.

## Как развернуть на Apploy

1. Создай **приватный** Git-репозиторий и загрузи в него файлы этой папки. Секрет `DIAG_TOKEN` в репозиторий НЕ добавляй.
2. В Apploy создай приложение из репозитория. Проект имеет `Dockerfile`, поэтому выбери вариант деплоя из Dockerfile, если панель предложит способ сборки.
3. Если в Apploy нет редактора переменных окружения, ничего настраивать не нужно: открой **логи контейнера** после деплоя. Найди строку `TEMPORARY_DIAG_TOKEN_FOR_PRIVATE_LOGS_ONLY=...`, скопируй значение после `=` и введи его на диагностической странице. **Не публикуй логи с токеном и не присылай токен в чат.** Если редактор переменных доступен, предпочтительнее задать `DIAG_TOKEN` в нём.
4. Если требуется порт, используй `3000` или укажи `PORT` в настройках. Приложение слушает `0.0.0.0` и `process.env.PORT`.
5. Дождись деплоя, открой предоставленный сервисом адрес и выполняй тесты по кнопкам.
6. Нажми «Скачать JSON для ChatGPT» и пришли файл. В отчёт секрет НЕ включается.

**На первом этапе не привязывай реальные домены**, достаточно тестового адреса платформы. Но работу собственного домена и TLS потребуется проверить до запуска рекламы.

## Что проверяется

- `GET /api/server`: запуск контейнера, uptime, ID процесса, RAM и cgroup-лимит, дисковое пространство, CPU, часовой пояс.
- `GET /api/network`: DNS для Битрикс24 и Яндекса, публичный исходящий IP, HTTPS доступность, пример внешнего POST с вымышленными данными. Адрес IP через ipify; внешний тестовый POST на postman-echo.com.
- `POST /api/echo`: имитация формы с тестовыми данными (на сервере ничего не хранится и в CRM не пересылается).
- `GET /api/ping`: ID контейнерного процесса и его uptime. Позволяет сравнивать до и после простоя.
- 20 последовательных запросов для оценки задержек на текущем подключении.
- `GET /health`: публичный минимальный endpoint для внешних мониторингов; не применяй мониторинг во время теста *засыпания*, потому что постоянные проверки могут держать приложение активным.

## Как интерпретировать

- `bootId` изменился после простоя: процесс перезапускался. **Это не доказывает, что причина именно засыпание**; возможны обновления, ротация контейнеров и т. д.
- Первый запрос дольше следующих: возможен холодный старт, но также влияют сеть и браузер.
- Исходящий IP помогает приблизительно оценить регион сети и провайдера. **Не доказывает, где физически хранятся данные**.
- HTTPS доступен до публичного сайта Битрикс24: **не гарантирует работу вашего конкретного вебхука** и создание лида в CRM.
- Нет ошибок при 20 запросах: только первичная проверка; не доказательство надёжности под нагрузкой.
- `memory.cgroupLimitBytes` может отражать реальный лимит контейнера; `cpuCountVisible` может отражать хост, а не тариф.

## Что проверить вне приложения

1. Условия бесплатного тарифа: коммерческое использование, политика сна, лимиты трафика и запросов, прекращение сервиса.
2. Юридически подтверждённое расположение обработки/хранения ПДн (не только IP).
3. Доступность из России: коллега с российской мобильной сетью и домашним интернетом должен сделать тесты и прислать отдельный JSON.
4. Работа через собственный домен Webhost1, DNS и автоматический HTTPS.
5. Для реальных лидов — отдельная проверка конечного вебхука, подтверждение создания записи в Битрикс24, обработка ошибок, очередь и повторы.

## Безопасность

- **НЕ** вставляй в тест реальный URL вебхука, токены или персональные данные клиентов.
- Диагностические API требуют Bearer токен `DIAG_TOKEN`. Если переменная не задана, токен генерируется при запуске и выводится в закрытые логи для временной диагностики. При рестарте токен меняется. Не публикуй логи с токеном и не используй этот шаблон хранения секретов для реальных вебхуков. Публичный `/health` раскрывает только `{ "ok": true }`.
- Отчёт содержит исходящий IP хостинга и общие сведения о сервере, но не токен, не реальные имена/телефоны и не значения переменных окружения.
- Внешние тесты отправляют технические запросы к Ya.ru, Bitrix24.ru, ipify.org и postman-echo.com.
